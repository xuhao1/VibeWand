**以语音与实体控制器为入口的本地跨应用协调层**

日期：2026年10月5日  
适用范围：产品定位、交互设计、技术架构与分阶段实现

> **One Wand to command them all.**

## V1.1 修订说明

V1.0 的定位、场景和安全原则保留。改动集中在三类问题：与仓库现状不符之处，可以用更少机制达到同样效果之处，以及缺失的内容。

| 位置 | 改动 | 原因 |
| --- | --- | --- |
| 1.4、3.7 | 新增对照基线和“现有不变量” | 命令模式要胜过的是已有的旋钮路径；安全规则应从现有代码延伸，而不是另起一套 |
| 5.1 | 常驻“命令模式”改为弹簧式命令键；按三种设备的真实控件重排映射；命令语音固定走内置识别 | VibeKey 只有旋钮和三枚按键，长按旋钮已是模型入口，没有独立的取消键和返回键；外置输入法模式下 VibeWand 拿不到转写文字 |
| 5.3、8.5 | 确认规则收敛为三条：导航直接做，提交确认一次，延后的前台动作重新确认 | 沿用“不替你发送”的现有承诺，用规则代替授权记录体系 |
| 4.1、7.2 | 去掉本地会话索引 | 有结构化列表的应用实时查询；其余应用用自带搜索，现有选择器导航已能完成后续动作 |
| 4.3、9.2 | 接力只走结构化委托；向输入框写字只用于草稿交接 | 桌面界面给不出可靠的回执、终态和取消；本机 Codex 已具备所需接口 |
| 3.4、10.3 | 协调模型默认只见元数据与引用 | 同时收窄隐私面、提示注入面和落盘日志 |
| 6.3、6.4 | 内核放到窄接口之后；不经 TypeScript bridge；不随包分发运行时；补充判据、备选和子进程的权限归属 | DSH 的 SDK 形态本身就是 stdio 上的 JSON-RPC；预览期组件需要退路；由 VibeWand 启动的进程会继承它的系统授权 |
| 6.5 | 新增首版工具表 | 工具清单就是 agent 的权限边界，V1.0 没有给出 |
| 6.6 | Peekaboo 从 M1 移到主链路稳定之后，以实验开关引入 | 首批应用已有辅助功能适配；它带来屏幕录制权限、宿主应用和版本矩阵 |
| 7、8 | 去掉 SQLite、授权记录、内容指纹与敏感级别；状态收敛到界面需要区分的几种；补充“谁来应答下游审批” | 首版单任务，追加写入的文件足够；结构化委托使 VibeWand 成为审批请求的接收方 |
| 10.1 | 写明命令模式改变了现有隐私承诺，默认关闭 | 现有代码和 README 承诺不读会话正文、不截屏 |
| 11.2 | 命令模式的验收平台与基础功能的最低系统版本分开 | 0.8.1 已按 macOS 13 以上发布 |
| 12 | M0 改为验证与取样；验证分三层；验收数字取自真实使用记录 | 先回答最不确定的问题；不建设持续向真实应用注入输入的自动化 |
| 13 | 补回阅读路径提到但正文缺失的“开放与合作” | “开源共建”与现行许可不符；贡献条款缺失 |
| 附录 | 区分“本次已核实”与“待运行验证”，更新资料来源 | V1.0 注明未复核仓库最新版本 |

### V1.2：作者确认后的四项变更

V1.1 留给作者复议的三项已有结论，另加一项新需求。它们取代上表中 6.3、6.6、11.2 三行的对应内容：

1. **内核随应用发布，不做应用内循环。** VibeWand 不自建模型 API 接入体系。首选随包的 DSH，备选随包的 Codex app-server（6.3、6.4）。
2. **命令键是普通的可绑定动作。** 各设备给默认值，键盘也有默认键：按住右 ⌥（5.1）。
3. **最低系统版本定为 macOS 26**，不再为旧系统保留兼容（11.2）。
4. **通用界面操作进入主链路。** “在 VS Code 里说一句就打开那个标签页”这类需求从 M1 起支持，后端为随包的 Peekaboo，只用控件树，不截图（4.5、6.5、6.6）。

### V1.3：M0 结论与 M1 实现记录

M0 的问题用一次性脚本和真实模型逐项回答过，M1 已按结论实现。使用说明见[命令模式](command-mode.md)，构建与测试见[开发指南](development.md)。

**M0 的结论，以及它们对正文的改动：**

| 问题 | 结论 | 影响 |
| --- | --- | --- |
| DSH 用哪个协议接入 | 它的 `acp` profile 就是标准的 Agent Client Protocol，有取消和按会话挂载 MCP 工具；SDK 协议没有取消，服务端也从不回调宿主 | 内核接口采用 ACP，6.4 已改写。将来换成其他支持 ACP 的运行时，只需改启动方式 |
| 宿主工具怎样注入 | 作为 MCP 服务挂到会话上。VibeWand 在 Unix 套接字上提供它，内核用系统自带的 `nc -U` 连接；套接字只接受内核自己的子进程 | 不开网络端口，不需要随包的转发程序 |
| 能否去掉自带工具 | 能。profile 写成不依赖任何 bundle 的完整插件树，共 17 个包，没有 shell、文件、网页、技能和子代理；测试核对这份清单 | 6.4 的“专属 profile”成立 |
| 是否有额外的数据外发 | 默认的最小树里有两个组件，会把会话日志和插件清单附在每次模型请求上；已从 profile 中去掉。内核仍会在自己的目录里生成随机安装标识并随请求发送 | 写入使用说明的隐私部分 |
| 延迟 | 随包内核从启动到会话就绪约 0.3 秒；三步导航（查找、打开、结束）在真实模型上约 4—7 秒，每步约 1 秒 | 按下命令键时即预热内核 |
| 工具调用能阻塞多久 | 内核的 MCP 客户端 60 秒超时，按会话挂载时不可配置 | 提问 45 秒无应答即视为取消；M3 的 `wait` 不能阻塞，必须结束本轮，事件到达后再发起新一轮 |
| Codex 的会话列表 | `thread/list` 0.2 秒返回标题、目录和更新时间；`searchTerm` 只做标题子串匹配且要 3 秒 | 取最近 60 条在本地按词筛选，没有匹配时把最近的交给模型判断 |
| 随包体积 | Node 24.21.0 为 117 MB，DSH 的最小包集 41 MB，应用合计约 170 MB | 只取启动器本身而不装它的全部依赖，否则再多三百兆 |

**M1 已实现：** 命令键（可绑定；VibeKey 长按旋钮并保持，手柄 L2，键盘右 ⌥）与只在开启时生效的键位层；命令语音走内置识别、按原词；浮层的听取、执行、选择、确认、完成各状态；随包内核与网关；6.5 表中 M1 的 13 个工具；任务记录与 14 天清理；设置页与开启时的发送内容说明；最低系统 macOS 26。

**与 V1.2 正文不同之处：**

1. **界面工具直接基于辅助功能实现，没有引入 Peekaboo。** 这是 6.6 预留的退路：五个工具约三百行，用的是 VibeWand 已有的授权，不增加随包的二进制，也不需要确认 Peekaboo 能否在不录屏的情况下工作。6.6 已改写。
2. **键盘用事件监听实现。** 需要回答问题时，方向键、回车和 Esc 交给命令并且不再传给前台应用；执行中只接管 Esc。其余时间不拦截任何按键。
3. **上限已定：** 每条命令 24 步、120 秒。（V1.5 起可在设置里调整。）
4. **内核不带图片存储**（`attachment-local`），协调器不发送图片，少带 18 MB。

**已验证：** 全部单元测试；用真实模型跑通的整条链路（进程、ACP、套接字与准入、网关、追问、取消），分别针对组装出的内核和签名后的应用包内的内核。

**写下 V1.3 时尚未在真实应用中观察结果的：**`codex://threads/<id>` 是否落到指定会话；VS Code 等 Electron 应用的标签页是否出现在控件树里；右 ⌥ 的按住检测与输入法是否冲突；各应用内搜索的关键词填入；真人语音下的端到端体验。前四项已实测，结论见 V1.4。

**尚未实现：** M2 的选区读取与草稿交接，M3 的结构化委托与等待，任务卡，个人偏好与别名，费用显示。附录A中“子进程的权限归属”等条目仍然有效。

### V1.4：M1 实测记录

2026-10-05 用真实内核和模型，在文本编辑、VS Code、Codex、Claude、飞书的真实窗口里逐项执行并读回结果，完整记录见[命令模式验收](command-acceptance.md)。测试用例 `CommandLiveTests` 需显式开启，用法见[开发指南](development.md)。

| V1.3 留下的问题 | 实测结论 | 处理 |
| --- | --- | --- |
| `codex://threads/<id>` 是否落到指定会话 | 是。窗口顶部显示的就是指定会话 | 附录A的这一项关闭。应用自身仍不读回落点，浮层照旧标注“结果未能核对” |
| Electron 应用的标签页是否在控件树里 | VS Code 的标签页读得到，按下即切换；Codex 窗口里的按钮同样可按 | 6.6 的原生实现成立。副作用：VS Code 会把读取当成屏幕阅读器，提示并进入“为屏幕阅读器优化”，已写入使用说明 |
| 右 ⌥ 与输入法是否冲突 | 冲突。豆包输入法用按住右 ⌥ 做语音键，按下事件在 VibeWand 之前被它取走；右 ⌘、⌃、⇧ 不受影响 | 键盘默认命令键改为右 ⌘（5.1 已改）；设置页说明按住无反应时换键 |
| 各应用内搜索的关键词填入 | Claude、Codex 正常。飞书的搜索不接受沿键盘路径来的粘贴，原实现报告“已填入”而搜索框是空的 | 输入后用字数和光标位置核对（不读内容），没有变化时改为发给应用再试一次，仍失败则如实告知；`ui_type` 同样核对 |

**实测中另外发现并已修正的：**

1. **从另一个桌面空间切来的应用。** 它成为前台应用比窗口到位早约 0.4 秒，这期间发出的快捷键会丢失或打开的搜索认不出来。所有把应用带到前台的工具现在等它的窗口到位。
2. **模型绕路。** 会把用户已经所在的应用再切一次；对有列表的应用（Codex），列表没有匹配时用界面工具自己拼搜索，因为工具说明把 `search_in_app` 限定给了没有列表的应用。已改提示词与工具说明，并在列表没有匹配时给出下一步。
3. **Codex 的列表只有本机会话。** 在远程机器上运行的会话不在 `thread/list` 的结果里，只能经 `⌘K` 搜索找到。6.3 里“Codex 走结构化列表”的说法因此只对本机会话成立。
4. **搜索框里残留的词**会和新词连在一起，现在先全选再填入。

**仍未验证：** 麦克风与真人语音下的端到端体验（实测用的是转录回放）；实体按键（键盘命令键用的是合成事件，被其他程序先取走的键只能用手按来验证）；应用包自己的悬浮面板和设置页在命令执行时的表现；以 DeepSeek Harness、WorkBuddy、微信为目标的搜索；VS Code 里的按键、菜单和输入文字。M2 的进入条件不变：作者日常使用 M1。

### V1.5：试用后的调整

作者试用 M1 后提出四点，0.8.5 据此修改。与 V1.2 正文和 V1.3 记录不同之处以本节为准。

| 提出的问题 | 改动 | 与原设计的关系 |
| --- | --- | --- |
| 模型只能用 DeepSeek | 模型由用户选：内置十几个服务的地址，或自定义地址加接口（OpenAI Chat Completions、OpenAI Responses、Anthropic Messages）；向服务拉取模型列表后挑选；密钥按地址存钥匙串。可调思考强度、上下文长度，可写附加参数和给模型的备注 | 内核仍是 DeepSeek Harness，模型适配从它的 DeepSeek 专用组件换成它自带的多服务组件。应用只描述“地址、接口、模型”（`ModelRoute`），内核的配置词汇仍只在 `KernelInstall` 里出现 |
| 需要权限档位 | 三档：每步确认（默认）、只确认有风险的（M1 原行为）、跳过全部确认 | 5.3、8.5 的“导航直接做”成为可选的一档而非唯一行为。是否询问由网关按档位决定，“什么算有风险”和问题的措辞在宿主一侧 |
| 看不到 agent 在做什么 | 悬浮窗的命令下方加一行：模型、上下文占用、第几步、权限档位。设置页加“Agent 记录”，逐条显示思考、工具调用与返回、确认与拒绝、上下文占用 | 任务记录因此开始保存工具返回的内容（V1.3 不保存），仍只在本机、14 天删除 |
| 默认关闭多一步 | 默认开启；模型没配好之前命令键和键位层都不生效，也不联系任何服务 | 原先以开关作为数据外发的闸门，现在以“用户配置了模型服务”作为闸门 |

**另外加的：** 对话保留时长（每条命令重新开始、5 分钟、30 分钟、2 小时）；对话用到上下文八成后下一条命令自动开始新对话；单条命令的用时上限（1 至 10 分钟）和步数上限（12、24、48）可调；设置里的“保存并测试”用当前配置让模型回一个字，失败时显示服务的原话。

**没有做的：**

1. **OAuth 登录。** Harness 的多服务组件带有账号登录流程，但它需要 Harness 自己的界面来走完，经 ACP 驱动不了。只支持 API Key。
2. **内嵌或打开 DeepSeek Harness 的网页界面来看历史。** 它的网页界面就是整个产品：全部依赖约 500 MB，而随包内核的包集是 130 MB；本机安装的 Harness 桌面版把运行时封在自己的包里，并使用自己的目录。因此历史和上下文改为在 VibeWand 自己的设置页和悬浮窗里显示。
3. **上下文压缩。** 内核没有挂压缩组件，接近上限时直接开始新对话。

**随包体积：** 多服务组件带来各家 SDK，包集从 41 MB 增至 130 MB，应用合计约 265 MB，安装包约 84 MB（0.8.4 不带内核，为 9.7 MB）。

**验证：** 内核经 DeepSeek 的 OpenAI 兼容与 Anthropic 兼容两种接口各跑通一次，含关闭思考、自定义上下文长度和错误密钥的报错；三档权限在文本编辑的真实窗口里读回了结果；V1.4 的文本编辑与键盘场景在新的模型路径上复测通过。DeepSeek 以外的服务和本机模型没有实测。

### V1.6：插件模式

0.9.0 起，内核可以二选一：VibeWand 自带的那一份（V1.5），或用户自己安装的 DeepSeek Harness。后者称为插件模式，是作者在 V1.5 之后提出的：V1.5 的“没有做的”里有两项，OAuth 登录和用 Harness 自己的界面看历史，都因为内置内核自成一体而做不了；让协调器作为插件跑在用户的 Harness 上，两项都由 Harness 自己解决。版本号也因此定为 0.9.0：从这一版起支持 computer use。同时，默认权限档位由 V1.5 的“每步确认”改回“只确认有风险的”。

| 问题 | 做法 |
| --- | --- |
| 怎样成为 Harness 的插件 | 用 Harness 自己的 bundle 机制。`kernel/plugin` 是一个 bundle：一份清单加一个补丁文件。VibeWand 在 Harness 的目录里写一个名为 `vibewand` 的 profile，只列这一个 bundle，再用 Harness 自带的 `dsh --profile vibewand` 经 ACP 驱动，和驱动内置内核是同一套协议 |
| 兼容性怎样声明 | 清单的 `peerDependencies` 写明验证过的 Harness 版本，Harness 在加载前自行核对，不符就跳过并说明原因；`engines.dsh` 写同样的内容供人阅读。VibeWand 启动前先问 Harness 的版本，不在已验证之列时不启动并告诉用户；用户选择尝试时，按 Harness 的规矩在 profile 的 `compatibility.json` 里为“这一插件版本 + 这一 Harness 版本”登记例外 |
| 模型从哪里来 | Harness 的模型配置写在它各个 profile 自己的补丁文件里，不跨 profile 共享。VibeWand 每次启动内核时，把用户桌面版（没有则网页版）配置里的模型服务行原样抄进 `vibewand` profile，并读出其中的默认模型；ACP 入口不会自己去取默认模型，所以由 VibeWand 指明。密钥和登录凭据在 Harness 的目录里是全局的，无需处理 |
| 能力边界变不变 | 不变。bundle 仍是一棵完整、显式的组件树（V1.3 的做法），没有用 Harness 的基础 bundle 打底：基础 bundle 带着命令行、文件、网页、技能、子代理等九十多行，靠“逐个禁用”去掉它们会随版本变化而漏掉新增的工具。只抄模型服务那几行，也是同一个理由：用户在自己 profile 里手工插入的插件不会被带进来 |
| 对话怎样出现在 Harness 里 | bundle 里包含 Harness 的会话库、会话索引缓存和标题组件，会话写在 Harness 自己的目录里。工作目录是名为 `VibeWand` 的文件夹。Harness 的界面把没有登记为工作区的会话列在“未分组”下。每一轮的消息改为以命令开头，因为 Harness 用开头的字作标题 |
| 空会话 | 内核在按下命令键时预热。若此时就建会话，没说话就松开会在用户的 Harness 里留下一条空会话，所以会话推迟到第一条命令才建立 |

**验证：** 用本机安装的 DeepSeek Harness 桌面版 0.2.0-rc.2，在测试自己的 Harness 目录里跑通：真实窗口里的输入与切换应用；对话写入 Harness 的会话库，并在它的标准网页界面里打开查看；声明了别的版本的 bundle 被 Harness 拒绝；本机那份 Harness 配置里的四个模型服务被正确带入并列出。详见[命令模式验收](command-acceptance.md)。

**没有验证：** 在真实的 `~/.dsh` 上运行；经 OAuth 或 DeepSeek 账号登录的模型服务；桌面版自己的窗口；终端安装的 `dsh`；第二个 Harness 版本。

## 摘要与设计结论

VibeWand 的出发点不是创建另一款通用 AI 助手，而是解决一个具体的个人需求：使用者希望靠在椅子上，以语音、旋钮和少量按键持续操作电脑，不必为了寻找会话、切换应用、复制上下文和确认操作反复回到键盘鼠标前。

随着工具能力增强，VibeWand 的价值可以从“操作各个 AI 软件的入口”延伸为“连接既有工具的胶水”。例如，用户只需表达“在 DeepSeek Harness 中运行这组测试，完成后把结果交给 Codex 分析”，VibeWand 负责定位项目、发起任务、核对状态、收集产物和完成交接，而不在内部重新实现测试代理或代码分析产品。

**产品定位是统一意图入口和跨应用协调层；实现方式是完整、受控的 agent loop；主要交互是语音与实体控制器。** 不以眼动、VR 或云端基础设施作为前置条件，也不将产品化等同于建立一家新的软件公司。

## 1. 为什么要做

### 1.1 从真实使用姿态出发

项目的原始需求是“更舒服地使用电脑”，而不是证明 AI 可以接管一切。使用者仍然阅读、判断和决定，只是不希望频繁改变身体姿态，或者为了表达一个简单意图执行一长串鼠标键盘操作。

因此，VibeWand 应优化的是完成任务所需的交互代价：寻找目标的时间、切换窗口的次数、复制粘贴的次数、语音澄清的轮数，以及不得不伸手接管键鼠的次数。降低这些代价，比单独追求无人干预的任务长度更符合项目初衷。

### 1.2 不缺少工具，缺少工具之间的连接

本项目所针对的使用者已经拥有自己的工具组合，例如 Codex、DeepSeek Harness、Claude、浏览器、Finder 与通信软件。这些工具不仅提供模型能力，还承载既有会话、项目状态、个性化设置和使用习惯。要求用户迁移到另一个统一客户端，会损失这些已有价值。

VibeWand 应接受这种异构性。用户继续选择自己喜欢的软件；VibeWand 帮助用户找到正确的入口、传递必要信息、跟踪交接过程。下游工具更新或替换时，主要调整适配器，而不是重建整个产品。

### 1.3 人工协调本身就是工作

“让 DSH 测试，再让 Codex 分析”包含大量容易被忽略的动作：确认工作目录、找到会话、表达测试范围、等待结束、定位日志、复制证据、切换目标会话、补充背景。这些动作并不要求 VibeWand 比两个工具更专业，却需要它持续理解用户意图与当前状态。

项目的核心假设是：**当跨应用协调变得可靠且低成本时，用户能够保留原有工具的优势，同时减少工具碎片化带来的操作负担。** 该假设需要通过日常使用和可重复测试验证，不能仅凭演示成立。

### 1.4 对照基线是现有的旋钮路径

VibeWand 0.8.1 已经可以单手完成切应用、开会话列表、选模型和听写。语音命令要胜过的不是键鼠，而是这条已有路径：双击旋钮切应用，单击打开会话选择器再转动，几下就能完成。

命令模式只在三种情况下占优：目标不在前几个候选里，需要跨应用搬运内容，或者需要等待后续步骤。设计和验收都以这条基线衡量；一条语音指令如果比转两下旋钮更慢或更不确定，就不该走模型。

## 2. 对前期讨论的反思与产品定位

### 2.1 从“超级 Siri”收敛为“跨应用协调层”

“超级 Siri”可以帮助解释语音入口，但容易让产品滑向自带所有能力的万能助手。VibeWand 更准确的定义是：**统一接收用户操作意图，结合局部上下文，驱动既有软件执行并完成必要交接的本地系统。**

它可以搜索会话、打开文件、提交任务、收集结果和转交信息。它不必重新提供代码编辑器、研究工作台、聊天客户端或浏览器。Computer use 是实现操作与交接的能力，不是要求所有任务都通过截图点击完成。

### 2.2 “不替代下游工具”不等于“只能做单次路由”

将首版简化为“语音转 JSON，再触发固定动作”，可以覆盖一部分命令，但不足以构成预期体验。应用可能没有打开，搜索结果可能不唯一，输入框可能改变，任务可能暂停等待授权。系统必须能够继续观察、调整和恢复。

因此，首版保留完整 agent loop。限制的是首批支持场景和工具面，而不是把闭环推迟到未来。完整闭环指的是循环结构——观察、决策、执行、核验、恢复；它不要求重型运行时，也不要求首版就开放通用界面操作。滚动、旋钮导航、实体停止等明确动作仍走本地快速路径，不为架构统一而额外调用模型。

### 2.3 “协调层”不意味着没有副作用

切换应用通常可逆；发送指令可能启动收费任务、修改工程或向外传输数据。VibeWand 不能因为“真正执行的是下游 AI”，就忽略自己发起操作的后果。系统需要保留任务范围、确认边界、接收回执和状态证据。

架构上可以区分协调层与专业执行层，但安全责任仍需贯穿整个委托过程。下游权限不应被 VibeWand 自动扩大，下游审批也不应被无差别自动批准。

### 2.4 产品边界

| 应当承担 | 不作为当前目标 |
| --- | --- |
| 定位应用、窗口、项目、会话与用户指定内容 | 重建所有应用的聊天和项目界面 |
| 理解意图，选择用户偏好的工具 | 自动认定某一家模型适合全部工作 |
| 交接指令与最小必要上下文 | 在协调器内另起一个完整编程或研究产品 |
| 跟踪任务、处理失败、支持中断和人工接管 | 无限制自主运行与不可解释的后台操作 |
| 维护自己发起的任务与交接记录 | 索引用户的会话历史或整台电脑、持续录屏、收集用户数据 |
| 先做好单机跨应用协作 | 首版建设跨设备云平台、眼动或 VR 入口 |

**项目可以大胆做能力，但应克制地增加职责。** 增加新功能前，应判断它是在减少表达、定位、交接和监督的成本，还是在复制下游已经提供的专业功能。

## 3. 设计理念与核心思想

### 3.1 一个意图入口，而不是一个替代一切的 agent

“One Wand to command them all”表达的是接口统一，而非功能垄断。用户不需要记住每个应用如何搜索和切换，但仍保留选择工具、理解结果和进入原应用继续工作的能力。

默认路由首先服从用户的明确指定，其次服从用户保存的偏好，再结合目标可用性和能力选择。存在实质歧义时展示候选，不由商业合作关系决定路由。

### 3.2 完整闭环与确定性执行相结合

协调器采用“理解意图 → 获取上下文 → 选择动作 → 校验与确认 → 执行 → 核验结果 → 继续或恢复”的闭环。模型负责处理不确定性，原生执行层负责约束目标、权限和副作用。

能通过稳定接口完成的动作，不重新用视觉定位；需要观察界面时，读取有身份的控件。没有可靠完成证据时报告“状态未知”或请求接管，不把模型判断当成事实。

### 3.3 语音表达意图，实体输入解决确定性决策

语音用于表达“做什么”，旋钮用于候选浏览，按键用于确认与停止。系统尽量把多轮口头澄清变成一组可选择的候选，但不能只凭模型自报的置信度执行有副作用的操作。

是否直接执行，取决于目标唯一性、证据新鲜度和动作后果。切换到明确窗口可以直接完成；向另一个服务发送内容，即使目标非常明确，也需要确认。

### 3.4 上下文走引用，不走屏幕坐标，也不默认走模型

应用名称、窗口坐标和最新一条消息不足以表示工作状态。系统应识别“哪个项目、哪次任务、哪份结果”，并在跨应用传递时保留原始证据与来源，不把连续摘要当成唯一信息载体。

更进一步：协调模型需要知道的是“有一段选区”“有一份日志在这里”，而不是它们的内容。“把这段报错交给 Codex 解释”这件事，协调器不必读报错。所以内容默认按引用流转，由网关在本地取出并送达，协调模型只看到用户原话、应用与会话的标题等元数据和工具回执。这同时减少了发给模型服务的信息、被内容中的指令误导的机会，以及落盘的日志。

### 3.5 本地优先、低维护负担

初期不建立 VibeWand 云账户，不经营统一 token 代理，不承担持续云端工作流。模型请求由用户配置的服务处理；任务记录由用户设备管理。

低维护来自缩小承诺范围：少量高质量适配器，固定的工具表，随包锁定版本的内核与界面后端，不自建模型接入体系，可复现的失败案例，以及清楚的支持边界。

### 3.6 功能上持续演进，交互上保持简单

发展路径为“找到和切换 → 携带上下文交接 → 跨应用任务接力 → 复用个人流程”。状态和适配器在内部演进；用户侧尽量保持“说一句、必要时选一下、随时能停”的稳定体验。

### 3.7 延续现有产品的不变量

现有代码里已有几条不靠模型保证的约束。命令模式在它们之上扩展，不另起一套：

- **不替用户发送。** 听写松开后不回车；命令模式写入的草稿同样停在输入框。
- **动作绑定按键时刻的目标。** 运行时在按下时记录应用、窗口和焦点的身份，执行前重新采样；身份变了，或采样超过半秒，动作丢弃。动作发给核对过的目标，不发给“当时的前台应用”。
- **代次失效。** 取消、断线、切换配置都会递增运行代次，迟到的回调据此作废。
- **不向密码框写入；** 输入法候选和未识别的弹窗只接受原生确认与取消。
- **不读会话正文、不截屏。** 输入框内容只归约为“是否为空”，候选标题只用于显示，诊断导出不含文字。
- **浮层不抢焦点。** 悬浮面板是不可激活的面板，从不成为 key window；候选由设备事件选择，来源应用的焦点和选区不受影响。
- **配置不执行脚本、不保存凭证；** 密钥在钥匙串，按规范化的服务地址绑定。

其中“不读会话正文、不截屏”在命令模式下会被有意放宽，范围见第10章。其余各条对协调器发起的动作同样适用。

## 4. 目标场景与任务边界

### 4.1 场景A：找到应用或会话

用户：“切到刚才讨论 VibeWand 麦克风的 Codex 会话。”

系统在按下命令键时记下来源上下文，之后按目标应用的能力走两条路之一：

- **应用提供结构化的会话列表。** Codex 的 app-server 可以按关键词和工作目录查询线程，返回标题、预览与更新时间。实时查询最近的会话，由模型在真实返回的条目中选出候选；唯一时直接打开，多个时在浮层列出标题、项目和时间，由旋钮选择。
- **应用没有这样的接口**（Claude、WorkBuddy 等）。打开应用自带的搜索面板并填入关键词，候选就是应用自己的搜索结果，用户像现在一样转动旋钮选择。VibeWand 不读取这些会话的正文，也不为它们建立索引。

打开后核对结果，不以“应用已经在前台”代替“会话已经正确打开”。“刚才”先在本机任务记录和会话的更新时间中解析；元数据不足以判断时展示候选，不默认读取会话内容。

### 4.2 场景B：把当前内容交给另一个工具

用户：“把这段报错交给 Codex，让它解释原因，先不要改代码。”

来源内容取按下命令键时的选区；没有选区时把当前文件或页面作为候选，必要时确认。“解释原因”和“不要改代码”作为原始约束逐字保留，协调器不得改写成“修复错误”。

VibeWand 把指令和内容写进目标会话的输入框，然后停住。用户在真实界面里看到将要发出的全部内容，可以照常编辑，按 OK 发送。这与听写“不替你发送”的规则一致，也让确认的对象就是实际内容本身，不需要另一套“内容摘要与审批绑定”的机制。

目标输入框已有草稿时不覆盖，改为询问追加、另开会话或放弃；目标会话正在运行任务时同样先问。发送后核对输入框已清空，再报告交接完成。内容较长时存成任务目录下的文件并给出路径；目标读不到本地路径时必须内联或上传。

### 4.3 场景C：DSH 测试，再交给 Codex 分析

用户：“在 DeepSeek Harness 中运行这个项目的测试，把失败结果给 Codex 分析。”

这类指令需要等待并取回结果，只走结构化委托（9.2）：以用户自己的 DSH 环境新建一个会话运行测试，拿到会话标识作为回执；结束后取得终态、退出状态和日志位置；再通过 Codex 的 app-server 新建线程提交分析要求并附上日志引用，拿到线程标识。全过程不向任何桌面输入框打字，最后用深链接把用户带到 Codex 的那个线程。

执行前在浮层展示整条计划：项目、测试范围、两端的工具、“不改代码”等约束，以及“将新建会话”这一事实。用户按 OK 确认一次；之后只有需要占用前台或偏离已确认的计划时才再次询问。等待期间不调用模型，由下游事件唤醒。

**测试有失败用例属于有效测试结果，不等于协调流程失败。** 不得以“测试必须通过”为理由自行启动修改与重跑。能用参数表达的约束就不只写在提示词里：“不改代码”对应只读沙箱。

“结果给 Codex 分析”在 Codex 确认接收后即完成；“等它分析完告诉我”则继续等到该线程的本轮结束。两种完成条件在任务记录中区分。

### 4.4 场景D：监督和连续修正

“不是这个，下一个”绑定当前候选集；“回到刚才”绑定导航历史；“先不要发”撤下待确认的计划；“停掉 DSH 这个测试”绑定任务记录里的那条委托回执。

候选集已失效、用户切换了目标或回执不明时，系统重新确认。不能把“下一个”解释为任意应用中的下一个条目，也不能把“停”当成对所有 AI 应用发送 Escape。

### 4.5 场景E：在任意应用里用一句话操作界面

用户在 VS Code 里：“打开 Runtime.swift 那个标签页。”

目标应用没有专门的适配器，也不涉及交接。协调器读取按下命令键时那个前台窗口的控件树，由模型决定怎么做：点击对应的标签，或者用它知道的快捷键（⌘P 加文件名）。每一步之后重新读取控件树核对结果，找不到目标就说明原因并交还用户。

这类操作遵守同一组规则：只操作按下命令键时的那个窗口，目标变了就丢弃；点击、快捷键和菜单属于导航，直接做；输入的文字停在输入框，不替用户回车；控件名属于删除、丢弃、关闭未保存内容一类的，先确认。

它的短板要事先说明：每一步都要经过一次模型，两三步的操作需要几秒；控件树里读不到的界面（画布、自绘控件）做不了。有专门适配器或结构化接口的应用仍然优先走那些路径。

### 4.6 首版边界

首版覆盖可靠导航、前台窗口内的界面操作、一次草稿交接和一条跨应用接力，并具备失败恢复与停止能力。同一时间只有一个协调任务。界面操作只在前台、在用户看得见的地方进行；后台只做结构化调用。首版不要求穷尽应用目录，不做通用自动修复，不依赖眼动、跨设备同步或用户编写流程脚本。

## 5. 语音与实体控制器交互

### 5.1 用按键区分听写与命令

保留现有“按住说话，把文字放入当前输入框”的听写。命令是另一个可绑定的按住动作：按住命令键说话，松开后这句话交给协调器，不写入任何输入框。两者由按的是哪个键区分，不靠模型猜测。“帮我修这个 bug”按麦克风键说，是给 Codex 的正文；按命令键说，是让 VibeWand 去找目标并委托。

不设常驻的“命令模式”。弹簧式按键不会留下忘记退出的状态，用户也不必在开口前先确认自己处于哪种模式。

| 操作 | 行为 | 约束 |
| --- | --- | --- |
| 按住麦克风键说话 | 听写到按下时的输入框（现有行为） | 松开不发送 |
| 按住命令键说话 | 松开后交给协调器 | 按下时记录来源应用、窗口、焦点和有无选区；浮层以不同样式标明“命令” |
| 命令键空按（未说话即松开） | 打开当前任务卡 | 没有任务时无动作 |
| 旋转 | 浏览候选 | 本地处理，不逐格请求模型 |
| OK | 确认候选或计划 | 确认对象变化后失效 |
| ESC | 停止当前任务，撤下待确认项 | 只在命令作用域内生效，不经过模型 |

“命令作用域”是现有手势作用域（阅读、编辑、会话、模型、强度、应用切换）之外新增的一个：浮层出现候选、计划或任务卡时进入，结束即退出。其余时间 OK 和 ESC 保持现有含义，草稿就位后的发送就是平时的 OK。导航历史的“返回”用语音表达，不占按键。

命令键是一个普通的可绑定动作，和听写一样出现在改键设置里，任何设备的任何按键都可以绑定。各输入方式只给默认值：

- **VibeKey：** 长按旋钮并保持说话，松开结束，沿用连续删除“长按触发后持有到松开”的做法。原先占用长按旋钮的模型入口让到 OK 长按。
- **手柄：** L2。L1 和 L2 目前都未分配。
- **遥控器：** 一枚未分配的按键，随实测 HID 配置确定。
- **键盘：** 按住右 ⌘。单独的修饰键不会往输入框里打字；Fn 留给外置听写。最初选的是右 ⌥，实测发现它是豆包输入法的语音键，按下事件到不了 VibeWand（V1.4）。键盘是新增的输入源，需要一个全局按键监听，使用已有的辅助功能授权；可在设置里改为其他右侧修饰键或关闭。

默认值的变化由现有的预设修订迁移处理，用户保存过的改键保留。

命令语音固定使用内置识别（系统听写或语音 API），按原词转写，不经过自动整理。听写仍然可以使用外置输入法；但外置模式下文字由输入法直接键入，VibeWand 拿不到，不能用于命令。未配置内置识别时，按命令键只提示先完成配置。

转写过程中可以预检权限和读取元数据，不在指令说完之前执行有副作用的操作。

### 5.2 最小而持续可见的反馈

浮层显示听取、定位、需要选择、待确认、执行、等待外部任务、需要处理、完成这几种状态，以及目标应用或会话和一行动作说明。默认不朗读回复；提示音可选。

等待外部任务时用户照常使用电脑，按键回到平时的含义。等待结束后，如果下一步要占用前台，浮层只提示“按 OK 继续”，不自行抢占——用户此刻可能正在别处打字。

### 5.3 少打断，但不隐瞒不确定性

三条规则决定是否询问：

1. **导航和只读操作：** 目标唯一且核对通过就直接做；有歧义时给少量候选。前台窗口内的点击、快捷键和菜单也属于这一类，但控件名属于删除、丢弃、关闭未保存内容一类的先确认。
2. **会启动下游工作或把内容送到另一个服务的提交：** 确认一次。一条指令包含多步时确认整条计划，不逐步询问。写入输入框的草稿不算提交，发不发由用户决定。
3. **延后发生且需要前台的动作，以及偏离已确认计划的动作**（换了目标、项目或内容范围）：重新确认。

首版不保存“以后都允许”的常用路线。每次提交多按一下 OK 是否构成负担，留给使用记录回答。目标再明确，也不因模型自报的置信度跳过第二条。

语音识别错误优先在应用名、会话名和项目名等实体上纠正；保留用户原话，不改写任务约束。用户中途打断时旧代次失效，迟到的模型结果不能继续操作电脑。

### 5.4 体验验收原则

一次普通命令不应演变为冗长对话；旋钮不能退化为另一个鼠标；命令键不能破坏听写；执行中始终能看见目标并停止。任何增加功能但显著增加模式记忆、确认次数或键鼠接管的设计，都应重新评估。

## 6. 拟采用的总体实现方案

### 6.1 组成

命令模式由五部分组成，其中前三部分在现有应用进程内。模块名是拟议的内部名称，不是现有组件的官方 API。

| 部分 | 位置 | 责任 |
| --- | --- | --- |
| 输入与浮层 | 现有 `Gestures`、`Runtime`、`Overlay`、`VoiceInputController` | 命令键、来源快照、命令转写、候选与确认、停止 |
| 动作网关 | 新增，应用内 | 工具白名单与参数校验、目标身份与新鲜度、确认规则、前台互斥、任务记录 |
| 应用适配器 | 现有 `ApplicationProfile`、`AccessibilityAdapter`，按应用增加结构化通道 | 会话查询、导航、草稿写入、委托、状态与取消 |
| 协调内核 | 窄接口后的可替换实现 | 理解意图、选择下一步工具、处理歧义与失败 |
| 外部工作 | 用户已有的 AI 与普通软件 | 编程、测试、分析、沟通 |

控制流：命令键松开后，运行时把原话和来源快照的元数据交给内核；内核每次提出一个工具调用；网关校验，必要时请用户确认，经适配器执行，再把回执和观察结果返回内核。浮层和任务记录由网关更新，不由内核更新。

### 6.2 复用现有机制

V1.0 的几个新概念在代码里已有对应物，扩展它们即可：

| 设计概念 | 现有机制 | 需要补充 |
| --- | --- | --- |
| 来源快照 | 听写开始时记录的 `TargetIdentity`（进程、窗口、焦点） | 有无选区及长度，文档路径或页面地址 |
| 执行代次 | `BridgeRuntime.generation` | 协调任务共用同一代次 |
| 观察新鲜度 | `requestRefresh` 加半秒时限与身份比对 | 无 |
| 候选导航 | `CandidateNavigation` 与各应用的选择器识别 | 浮层内的候选列表 |
| 内容投递 | `ClipboardTextDelivery`：保存剪贴板、标记临时内容、恢复，用户期间复制了新内容则不覆盖 | 无 |
| 适配器验证声明 | `ApplicationProfile.verification` | 细化到能力 |
| 凭证 | 钥匙串，按规范化地址绑定，拒绝重定向 | 协调模型的条目 |
| 对兼容 chat/completions 服务的调用 | 自动整理使用的 `SpeechTextProcessor` | 带工具的请求 |

也有现有代码做不到的：应用切换目前是对 ⌘Tab 的驱动，适配器只面向前台应用，采样时只取选区的范围而不取文字。按应用标识激活和读取选区文字是新增能力，量不大；后台界面操作不在首版范围。

### 6.3 协调内核

内核的职责很窄：拿到原话、元数据和工具清单，逐步提出工具调用，直到结束或交还用户。接口只有四件事——开始一次任务，提交工具结果，取消，产生事件流。网关、工具、浮层和任务记录都不依赖内核的具体实现。

两条约束已经确定：VibeWand 不自建模型 API 接入体系，模型适配、凭证和循环都交给现成的 agent 运行时；内核随应用发布，版本由发行包锁定，不依赖用户另行安装。应用内自写循环因此不在考虑之列。接口有三个实现：

- **脚本内核。** 回放录制的工具调用序列，只供 `swift test` 使用。
- **DSH，首选。** 作者日常使用；DeepSeek 原生接入，自带凭证管理，适合高频调用的协调器。[2][3]
- **Codex app-server，备选。** 单个原生二进制，本机协议定义中有宿主动态工具调用，可复用 ChatGPT 登录；接力场景本来就要实现它的协议客户端，同一份代码可以兼作内核。代价是模型基本限于 OpenAI，并消耗订阅额度；自带的命令执行能否关闭待查。

随包发布把 DSH 预览期的不兼容变更变成了“升级时才面对”的问题，剩下的代价是：随包带 Node 运行时使包体增加约一百兆量级，嵌套的 Node 需要随应用签名，以及专属 profile 的裁剪与审计。DSH 由 M0 的判据确认：

- 导出的工具清单恰好等于 6.5 的列表，自带 shell 彻底移除；
- 宿主工具能往返调用，取消能中止进行中的一轮；
- 冷启动、每轮额外延迟和常驻内存可以接受；
- 会话日志落在 VibeWand 自己的目录且可清除，不触碰用户的 `~/.dsh`；
- 随包的 Node 与 `dsh` 在应用签名下能正常启动。

任何一条不满足就改用 Codex app-server。OpenCode、Goose 等可随包的单二进制运行时不并行维护，只在两者都不成立时评估。M0 还要确认 DSH 的 `acp` profile 是否就是 Agent Client Protocol：如果是，内核接口直接采用这个公开协议，将来更换内核不必改动 VibeWand。

### 6.4 DSH 的接入方式

- **经 Agent Client Protocol 驱动。** DSH 的 `acp` profile 实现标准的 ACP：`session/new`、`session/prompt`、`session/cancel`，以及按会话挂载的 MCP 工具。Swift 直接在子进程的标准输入输出上说这个协议，不需要 TypeScript bridge。SDK 协议不适用：它没有取消，服务端也不向宿主发请求。[3]
- **随包发布，锁定版本。** 应用包内带固定版本的 Node 与 `dsh`，不使用用户机器上的安装，升级随 VibeWand 的版本进行。两者的许可文本按 `third-party/` 的现有方式随包保留。
- **专属 profile，不用现成的。** `sdk-minimal` 并不安全：它自带一个可以修改进程可达的任意路径的 shell。[4] 协调器的 profile 不叠加任何 bundle，自己写出完整的插件树：模型适配、会话、协议桥，共 17 个包，没有任何自带工具，也不含向模型请求附带会话日志和插件清单的组件。测试逐项核对这份清单，多出一个包就失败。
- **宿主工具以 MCP 服务提供。** 网关在一个 Unix 套接字上提供工具，会话建立时把它作为 MCP 服务交给内核，内核用系统自带的 `nc -U` 连接。它不监听网络端口；套接字只接受内核进程自己的子进程，因为连上它就等于拿到了 VibeWand 的辅助功能授权。内核对一次工具调用最多等 60 秒。
- **凭证**从钥匙串读出，启动子进程时经环境变量传入，不写进 DSH home，不出现在命令行参数和日志里。
- **协议**要有版本握手、任务标识、执行代次和超时；标准输出只走协议，诊断走单独的通道。

**子进程会继承 VibeWand 的系统授权。** 按 macOS 的责任进程规则，由 VibeWand 直接启动的进程在隐私授权上一般归属于 VibeWand：它们可以使用 VibeWand 的辅助功能授权，访问受保护目录时系统提示也以 VibeWand 的名义出现。实际继承范围列为 M0 的验证项。内核进程因此绝不能带 shell 或其他能执行任意代码的工具——这不只是整洁问题。同样的规则也约束下游委托的启动方式，见 9.2。

**两个 DSH 实例必须分开。** 协调内核使用 VibeWand 自己目录下的 home、会话和 profile；被委托去跑测试的 DSH 使用用户自己的 home，作为用户的工具运行。前者不加载用户项目里的工作指令、技能或插件，也不读后者的会话；需要的内容由适配器按任务范围提供。

### 6.5 首版工具面

协调模型能做的事以这张表为限，网关拒绝表外的调用。

| 阶段 | 工具 | 作用 | 副作用 |
| --- | --- | --- | --- |
| M1 | `list_targets` | 已适配应用的运行状态、各自具备的能力、当前前台 | 无 |
| | `find_sessions` | 在有结构化列表的应用中按关键词、项目查询会话 | 无 |
| | `open_session` | 经深链接或适配器导航打开指定会话并核对 | 切换前台 |
| | `search_in_app` | 打开应用自带的搜索并填入关键词，由用户用旋钮选择 | 切换前台 |
| | `activate_app` | 把应用带到前台，可附带要打开的文件或地址 | 切换前台 |
| | `choose` | 在浮层给出候选，返回用户的选择 | 无 |
| | `finish` | 结束并给出一行结论 | 无 |
| | `need_user` | 交还用户并说明缺什么 | 无 |
| | `ui_snapshot` | 读取来源前台窗口的控件树：角色、名称、状态与元素标识 | 无；控件上的文字进入模型 |
| | `ui_press` | 按元素标识点击控件 | 操作界面；破坏性控件需确认 |

| M2 | `source_snapshot` | 来源的元数据：应用、窗口标题、有无选区及长度、文件路径或页面地址 | 无 |

| | `wait` | 挂起循环，直到回执对应的任务变化或超时 | 无 |
| | `result` | 终态、退出状态与产物引用 | 无 |
| | `cancel` | 请求下游取消，并报告是否得到确认 | 取消下游工作 |

表里没有 shell、任意文件读写和坐标点击。五个 `ui_` 工具只作用于按下命令键时的那个前台窗口，由通用界面后端执行（6.6）。选区、日志和附件以引用出现在参数里，由网关在本地取出并送达。确实需要模型阅读内容的场景（例如按报错内容挑选会话）另加一个显式的读取工具，调用时在浮层标出；首版不提供。

### 6.6 通用界面后端

首批四个 AI 应用和浏览器有手写的辅助功能适配；其余应用（场景E）由通用界面后端支持，从 M1 起提供。它是可靠性最弱的一环，所以范围收得很紧。

后端直接基于 macOS 的辅助功能接口实现，就是读屏软件拿到的那棵控件树：

- 五个工具：读取前台窗口的控件（角色、名称、状态），按元素按下，发送一个快捷键，按标题路径选择菜单项，向输入控件输入文字。
- 不截图，不点坐标，不新增系统权限。控件树读不到的界面不在支持范围内。
- 不读输入框和文档的内容：输入框只报告是否为空，密码框不接受输入。
- 调用经同一个网关，受同样的身份、确认和前台互斥规则约束，只作用于来源前台窗口或任务切到的那个应用。
- 破坏性与提交类控件的确认名单按控件名匹配（删除、丢弃、不保存、发送、提交、支付等），在本地执行，不交给模型判断。多行输入框里的回车、⌘回车、⌘⌫ 和 ⌘Q 同样先确认。
- Electron 应用沿用现有做法，首次接触时请求其公开控件树。

V1.2 曾计划随包使用 Peekaboo 的工具层。[5][6] 它覆盖的元素识别更广，但需要再带一个二进制，并且要先确认它能在不录屏的前提下工作。在控件树路径被证明不够用之前不引入。

## 7. 核心数据对象与上下文机制

### 7.1 用有来源的引用替代模糊名称

会话、任务和产物用带来源的引用表示：应用标识，应用给出的原生标识（线程 ID、会话 ID、文件路径），以及展示用的标题。应用不提供原生标识时如实标记为未知，不根据窗口标题补造；这类目标只能通过应用自带的搜索由用户选定。

界面观察沿用现有的 `TargetObservation`：采样时间、进程与窗口身份、焦点。每个界面动作在提交前重新采样并比对，不复用旧的坐标或元素。

### 7.2 三类上下文分别管理

**即时上下文：** 按下命令键时的来源窗口、选区、页面或文件。浮层从不取得焦点，所以来源应用的焦点和选区在整个选择过程中保持不变；执行交接前仍然重新核对来源身份。选区优先通过辅助功能读取；应用不暴露选区时退回一次复制并恢复剪贴板，只在命令任务内使用。

**工作上下文：** 项目、会话、委托回执和产物。会话实时向应用查询，不预建索引，不复制历史；本机只保存 VibeWand 自己发起过的任务记录。

**个人偏好：** 常用工具、项目别名、默认路由。可见、可编辑、可删除。临时说过一次“用 Claude”不等于修改默认工具。

模型的最终选择必须落在工具真实返回的候选集合中。只有在使用记录表明关键词和时间不够用时，才考虑摘要或向量检索。

### 7.3 交接包是跨应用协作的基本单元

`HandoffEnvelope` 把原始要求、约束、来源、目标和完成条件作为一个整体传递。以下为概念示例，不是 DSH 或 Codex 的现成协议：

```json
{
  "instruction": "分析测试失败原因，先不要修改代码",
  "constraints": {"allow_code_change": false},
  "source": {"app": "dsh", "receipt": "session-id"},
  "target": {"app": "codex", "session": "new"},
  "workspace": "/path/verified-by-adapter",
  "revision": "commit-or-unknown",
  "artifacts": [{"ref": "test-log", "delivery": "path"}],
  "completion": "target_acknowledged"
}
```

`instruction` 是用户原话中的要求，逐字保留；`constraints` 是其中能映射为下游参数的部分。`delivery` 说明内容怎样到达目标：本地工具给路径，读不到本地文件的目标必须上传或内联，不能只粘贴一个对方打不开的文件名。摘要可以附带，但原始日志和证据必须能被定位。

### 7.4 任务记录与模型会话不是同一个东西

内核的会话日志保存模型上下文。任务记录是另一份东西，由网关写入，保存原话、每一步的工具与目标引用、提交状态、下游回执和产物位置。界面上的“已提交”“已完成”只从任务记录得出，不从模型的最后一句话推导。

首版同一时间只有一个任务，记录用追加写入的 JSON Lines 文件，每个任务一个目录，产物放在其中。提交前先写入意图，收到回执后补记；崩溃后读最后几行即可恢复现场。不需要数据库或常驻服务。记录默认不含选区和日志的正文，只含引用。

## 8. Agent loop、任务状态与可靠执行

### 8.1 闭环按证据推进

每一轮：内核看到任务当前状态和上一步的回执，提出下一个工具调用；网关检查前置条件和确认规则后执行，返回证据。成功就推进；失败就在步数上限内换路径、重新定位或交还用户。

内核只能提出动作，不能把任务写成“已完成”。完成由适配器回执、可核对的界面状态、结果文件或用户确认满足；无法验证时停在“需要处理”，并说明缺什么。

### 8.2 区分协调任务、单次提交和下游工作

| 对象 | 状态 | 含义 |
| --- | --- | --- |
| 协调任务 | 进行中 / 等待 / 需要处理 / 完成 / 已取消 | 整条指令的推进情况 |
| 单次提交 | 待提交 / 已确认送达 / 送达未知 | 这次操作是否真的到了对方 |
| 下游工作 | 运行中 / 等待审批 / 完成 / 失败 / 未知 | 被委托工具的实际状态 |

状态只保留界面需要区分的这些。“正在等待 DSH”是正常状态；“DSH 测试失败”可以产生有效的交接包；“无法确认是否送达”进入“送达未知”，不立即重发。下游状态不可观测时记为未知，不从修改时间、按钮颜色或聊天措辞推断终态。

结构化委托让 VibeWand 成为下游审批请求的接收方：由它启动的 Codex 线程会把命令执行和文件修改的审批发给它，而不是发给桌面应用。首版的处理是，委托时用沙箱和审批参数把范围定死（分析任务只读），不代答任何超出范围的请求；出现时任务进入“需要处理”，浮层展示原始请求，由用户决定。

### 8.3 副作用去重与恢复

每条指令一个任务标识，每次提交一个稳定标识。提交前写入任务记录，收到回执后记下下游标识。重试之前先查证原操作是否已经生效；接口支持幂等键时使用它。

界面操作没有跨应用事务，做不到严格的恰好一次。“可能已发送但回执丢失”时查询目标会话或请用户确认，不宣称绝对不会重复。用户明确说“再跑一次”是新的提交，不算重复。

### 8.4 等待不等于持续推理

结构化委托有事件就订阅事件，没有就做带退避和上限的状态查询。只有状态变化、超时、审批请求或新指令到达时才回到模型循环。等待期间不占用前台。

应用退出或电脑休眠后不承诺继续接力。重新启动时列出未结束的任务及其回执，核对下游现状后由用户决定继续还是放弃，不自动重跑。下游可能仍在运行，也可能已经结束。

### 8.5 前台互斥与用户优先

同一时间只有一个任务，也只有它能操作界面。界面动作绑定目标进程、窗口和观察代次；用户切换了目标、编辑了输入框或按了停止，后续动作作废。

延后发生的前台动作一律等一次实体确认（5.3）。按下 OK 既是授权，也说明用户此刻手在设备上，而不在键盘上。

剪贴板恢复沿用现有做法。确认绑定实际目标和待发送内容；目标、附件或正文变了，原确认作废。

## 9. 应用适配与 Computer Use 执行策略

### 9.1 适配器声明能力，不伪装全能

每个适配器按能力声明自己做得到什么、在什么条件下可用、是否经过实机验证：查询会话、导航、读取来源、写入草稿、结构化委托、读取状态、取消、取回结果。现有的 `ApplicationProfile.verification` 已经按应用记录验证情况，命令模式把它细化到能力。

能切换会话不代表能读取运行状态。某项能力缺失时，内核从 `list_targets` 的返回里就能看到，改走已有的替代路径或交还用户，不编造调用。

### 9.2 三种通道与选择规则

适配器有三种通道，按“能否给出可靠回执”选择，而不是逐层尝试：

- **结构化接口：** 官方命令行、SDK、app-server、文档化的深链接。能给出标识、事件、终态和取消。查询会话、打开指定会话和一切需要等待的委托都走这里。
- **现有辅助功能适配：** 选择器识别、候选导航、按钮按压、粘贴投递。能核对界面状态，给不出下游任务的终态。用于应用内搜索和草稿交接。
- **通用界面后端：** 控件树快照加按元素操作（6.6）。用于前两者都不覆盖的应用，只作用于来源前台窗口。

由此得到一条硬规则：**需要等待和取结果的接力只走结构化接口；向输入框写字只用于草稿交接，写完即止。** 桌面界面没有可靠的“已接收”“已结束”和“已取消”信号；靠观察按钮和文字去推断终态，正是 V1.0 里最多“待验证”的来源。

结构化委托会在目标工具里新建会话，使用用户自己的账户、配置和工作目录，但不是用户正开着的那个窗口。浮层在确认计划时写明“将新建会话”，结束后用深链接把用户带过去。不把新启动的进程冒充为用户正在使用的桌面会话，也不去续写桌面端可能正开着的线程。

委托进程由谁启动也有讲究。下游 agent 本来就要执行命令；如果它是 VibeWand 的子进程，它会继承 VibeWand 的辅助功能授权，它访问文件时系统提示的也是 VibeWand（6.4）。所以优先连接工具自己管理、已在运行的服务——Codex 的 app-server 有 `daemon` 与 `proxy` 子命令用于此——让下游工作留在它自己的身份和权限之下。只有确认了权限归属之后，VibeWand 才自行拉起这类进程。

任何通道涉及新增系统权限、更大的读取范围或新的接收方，都要重新确认，不能借“回退”扩大权限。首版不做坐标点击。

### 9.3 首批适配对象

| 对象 | 导航 | 草稿交接 | 接力 | 核实情况 |
| --- | --- | --- | --- | --- |
| Codex（桌面版的应用包现为 ChatGPT.app，标识 `com.openai.codex`） | `thread/list` 查询，`codex://threads/<id>` 打开；回退到 ⌘K 面板 | 现有粘贴投递 | app-server：`thread/start`、`turn/start`、`turn/completed`、`turn/interrupt` | 方法见本机 0.156.1 生成的协议定义，路由字符串见桌面包；跳转效果、新线程在桌面端是否可见，均未运行验证 |
| DeepSeek Harness | 现有的侧边栏会话列表；`dsh://open` 待查 | 现有粘贴投递 | 以用户的 home 运行 `headless` 或 `sdk` profile | profile 名称见官方架构文档；回执、事件与取消语义未验证 |
| Claude、WorkBuddy | 现有的应用内搜索 | 现有粘贴投递 | 首版不做 | Claude 的包内只见新建与继续最近会话的路由；WorkBuddy 的路由未检查 |
| 浏览器、Finder、其他 macOS 应用 | 激活，打开指定文件或地址 | 读取选区和页面地址 | 不适用 | 读取选区是新增能力 |

Codex 的 `thread/read` 读取已存线程但不订阅，`thread/resume` 才载入并继续；线程的运行状态由持有它的 app-server 进程报告，不是跨进程的全局状态。[7] 因此接力使用自己新建的线程。能否经 `proxy` 观察桌面端正在运行的线程，列为 M0 的验证项。

### 9.4 普通软件与 AI 软件保持一致的操作语义

对普通软件，除了激活应用和打开指定的文件或地址，前台窗口内的操作（切换标签页、暂停媒体、修改明确的设置）由通用界面后端完成。“专业工作交给下游”针对的是重复建设业务能力，不是禁止普通桌面操作。

调用既有 AI 软件时不绕过登录、权限提示或服务条款。

## 10. 隐私、安全与用户控制

### 10.1 命令模式改变了现有的隐私边界

现有版本的承诺是：没有服务器和账号，不读会话正文，不截屏，听写文字只进输入框。命令模式第一次让屏幕上的信息离开本机——用户的命令原话、应用与会话的标题、项目路径，以及界面操作时前台窗口的控件文字，会发给用户配置的协调模型；交接的正文会发给用户指定的目标工具。这是对现有承诺的有意改变，所以：

- 命令模式默认关闭，开启时列出会发送什么、发给谁；
- 未开启时现有行为和承诺不变，基础功能的界面采样不因此读取更多内容；
- README 的隐私说明在功能发布时同步修改。

跨应用胶水最敏感的动作是跨越信息边界：用户允许一个工具处理某份材料，不等于允许所有工具读取它。首版用确认规则守住这条边界——内容送往哪个工具，用户都在计划或草稿里亲眼看到并按键确认。

VibeWand 可以承诺的是“不向自营服务器收集用户内容，只传递任务所需的数据，提供可查看和清理的本地记录”。这不等于完全离线，也不等于上游模型或下游应用不保存数据。

### 10.2 不作未经确认的零数据留存承诺

V1.0 核查时，未从所核对的 DeepSeek 开放平台服务协议取得“所有 API 请求默认零数据留存”的明确依据；本次未重新核查。是否存在适用于特定账户、模型、渠道或单独协议的安排，需要分别确认。[8]

应区分“不用于训练”“保留请求内容的期限”“安全审计日志”和“第三方应用自己的记录”。不能把协调模型的条款套用到语音识别、附件存储和下游 AI 软件，也不能因用户自带 Key 就省略数据流说明。

### 10.3 分层处理数据

| 数据类型 | 处理方式 |
| --- | --- |
| 音频 | 沿用听写：只在内存，不落盘 |
| 命令原话 | 发给协调模型；写入本机任务记录 |
| 实体元数据（应用、会话标题与预览、项目路径、时间） | 按任务发给协调模型 |
| 选区、日志、附件 | 不进协调模型；由网关按引用送到用户确认的目标 |
| 前台窗口的控件树（控件名、标签页标题、菜单项等界面文字） | 仅在场景E的任务中读取，发给协调模型；不含输入框和文档正文 |
| 屏幕截图 | 不使用 |
| 凭证 | 钥匙串；经环境变量传给内核进程；不进提示词、命令行参数和日志 |
| 任务记录与内核会话日志 | 本机固定目录，可查看、可一键清除，保留期限可设 |
| 诊断导出 | 沿用现有规则，不含文字内容 |
| 使用统计 | 仅本机，从任务记录计算；社区反馈由用户主动选择和提交 |

DSH 的原则是“模型可见即入日志”。[3] 所以减少落盘内容的办法不是关日志，而是让正文根本不进模型上下文；这也是 6.5 不提供读取正文工具的原因之一。

### 10.4 工具网关是执行边界

网页、聊天消息、测试日志和附件都是不可信内容。主链路里它们按引用搬运，不经过协调模型，被注入的机会本来就少；一旦进入模型（标题、预览、将来的读取工具），它们只能作为证据，不能改变用户意图、扩大工具清单或要求读取凭证。约束在网关里执行，提示词里的“忽略以上规则”改变不了它。

失败后的降级不得扩大权限：不因为结构化路径失败就改用全屏截图、广泛的文件访问或任意脚本。

### 10.5 取消与撤销分别设计

ESC 立即阻断尚未执行的本地动作，使旧代次失效，并对已委托的任务发送受支持的取消请求；后台等待中的任务通过任务卡停止。未收到下游确认时显示“本地已停止，下游停止未确认”。

已经上传的数据、已发送的消息和下游已修改的文件不一定可撤销。只对明确支持的动作提供撤销或补偿，不把统一的 Command-Z 当成跨应用回滚。

## 11. 本地部署、模型与维护成本

### 11.1 不建设自营公共后端

没有 VibeWand 云账户、跨设备同步中心、token 中转站和云端任务队列。发行包、文档和问题反馈使用现成的托管设施。本地内核进程是产品运行组件，不等于开发者经营公共服务器；它不监听网络端口。应用应清楚提示哪些任务依赖本机在线，哪些下游任务独立运行。

### 11.2 平台、权限与打包

最低系统版本定为 macOS 26，以作者的 macOS 27 环境开发和验收，不再为更早的系统保留兼容。原生液态玻璃、蓝牙麦克风组件和构建用的 SDK 都已经以 26 为准。0.8.1 是最后一个支持 macOS 13—15 的版本。

不新增系统权限，仍然是辅助功能与麦克风。发布包若是临时签名，更新后可能需要重新登记辅助功能；随包的内核作为子进程依赖应用的授权，所以对外发布带内核的版本之前应换成稳定的签名身份。内核里的 Node.js 保留其官方签名。

内核（DSH 连同 Node）随包发布并锁定版本，由 `scripts/build-kernel.sh` 按固定摘要组装。被委托的下游工具——用户的 DSH 环境和 `codex`——仍然使用用户自己安装的版本，启动时探测并核对，经过验证的组合写进兼容表。

### 11.3 模型角色与费用边界

主链路不需要图像输入。协调模型需要的是中文语境下稳定的工具调用，以及对转写噪声下的应用名、会话名的容错；默认推荐在 M0 用真实指令样本评测后确定。采用 DeepSeek 等兼容服务是可选配置，不将某个品牌名称等同于所有模型都具备相同能力。

作者开发所消耗的 token、用户运行协调器消耗的 token、下游应用的订阅与推理费用，分别核算。用户直接使用自己的凭证和账户，不共享作者的 Key，也不承诺软件免费就包含无限模型调用。

### 11.4 预算和等待策略

每条指令三个上限：步数、主动执行时长、外部等待期限；单步失败最多换一条路径。默认值用 M1 的使用记录确定，不写成性能保证。确定性动作不调用模型，等待不调用模型，同一个无效动作不重复。费用在任务卡中可见。

### 11.5 控制维护范围

维护少量高频适配器和固定的测试环境，不承诺所有软件、所有历史版本和所有外设都可用。不允许 agent 自行安装插件或工具。对无法稳定验证的功能标为实验性，比提供看似万能却频繁误操作的入口更可持续。

## 12. 实施路径与验证方法

### 12.1 先回答最不确定的问题，再按可验收能力推进

| 阶段 | 主要交付 | 进入下一阶段的条件 |
| --- | --- | --- |
| M0：验证与取样（约一周，不写产品代码） | 随手记下日常工作中想用语音下达的真实指令；用一次性脚本回答附录A的问题；VibeKey 命令键上手比较 | 内核与键位有结论；有三五十条真实指令作为评测集；本文据此更新 |
| M1：语音导航与界面操作 | 命令键（含键盘默认键）、浮层状态、随包内核、网关；导航类工具与五个界面工具；Codex 结构化查询与跳转，其余应用走自带搜索或控件树 | 作者在日常工作中持续使用；没有误操作；比旋钮慢的指令类别已经识别 |
| M2：草稿交接 | 来源快照、选区读取、交接包、写入草稿并核对 | 能把指定内容连同原始约束交到正确会话的输入框，不覆盖已有草稿 |
| M3：跨应用接力 | 结构化委托、等待、取结果、转交、重启后的现场恢复 | DSH 测试到 Codex 分析的链路可核对；送达未知时不重发；下游审批不被代答 |
| M4：开放准备 | 稳定签名的发行包、下游工具探测与兼容表、适配器文档、贡献条款 | 他人可以独立安装、使用、复现问题和贡献 |

M1 起就是完整闭环，不是先做固定命令再推翻重写。首条链路做深，优先于同时接入更多应用。

### 12.2 验证分三层

1. **`swift test`，默认门槛。** 覆盖网关规则、任务记录的崩溃恢复、协议编解码、代次失效和确认绑定。用脚本内核回放录制的工具调用序列，配合假适配器覆盖同名目标、下游忙碌、测试失败、超时、窗口变化、草稿存在、权限撤销、用户中断和进程重启。
2. **按适配器的实机验收。** 沿用 `WorkBuddyLiveTests` 的做法：显式启用，指名目标应用，发现用户草稿即拒绝，不发送消息，结束后恢复现场；默认测试不触碰任何真实应用。
3. **真实使用记录。** 正确率、澄清次数、键鼠接管次数、费用和延迟，从作者日常使用的任务记录里统计。

不建设持续向真实应用注入输入的自动化通道。仓库在 0.8.0 之前移除了应用内的自动化通道（提交 `0d8b55b`），原因之一正是这类事故：按键发给了“当时的前台应用”，落在用户正在输入的地方。

### 12.3 建议验收门槛

以下是目标，不是已达到的指标，数据取自真实使用记录而非合成运行：累计一百条以上的导航指令，正确完成率不低于 95%；数十次接力，正确交接率不低于 90%。分别报告自动完成、经候选选择完成和键鼠接管完成，并记录系统、模型和应用版本。

未经确认的发送、提交到错误目标、停止后继续注入输入——出现任何一次都阻止对应版本发布。有限使用中未出现事故不等于证明零风险，仍需明确适用范围。

延迟分段测量：本地反馈、转写完成、模型首轮、动作执行、下游等待。设计目标是按下命令键立刻有反馈，简单导航在松开后两三秒内出现第一个可见动作；达不到的指令类别退回旋钮路径。模型本身慢与界面没有反馈是不同的问题。

### 12.4 最重要的个人使用验证

在一段连续的日常使用中，观察作者是否自然选择命令键，同一类任务里语音命令与旋钮路径各用了多少次，是否明显减少键鼠接管，失败后是否愿意继续使用，以及维护是否挤占主业。若技术指标提高但实际使用意愿下降，应优先调整交互和职责边界，而不是继续扩充功能。

### 首轮建议验证的四个端到端场景

第一，按住命令键说出要找的会话：Codex 走结构化查询，其余应用走自带搜索，多个候选时用旋钮确认。第二，从原应用取选区，写入另一个 AI 的输入框并停住，不覆盖原有草稿。第三，运行“DSH 测试 → Codex 分析”，故意加入测试失败、下游请求审批和网络中断。第四，在计划确认前、提交后送达未知时和下游执行中分别按 ESC，核对实际状态与浮层描述一致。

### 方案中的明确否定项

不把单次 JSON 解析当作完整方案；不将功能建立在纯视觉点击上；不让两个 agent 同时操作桌面；不从任务文本推定授权；不向“当前前台应用”而是向核对过身份的目标发送输入；不因下游已开始工作就丢失监督；不代答下游审批；不宣称界面操作能严格一次执行或所有动作可撤销；不以源码公开、用户自带 Key 或学校合作自动等同于无隐私和合规责任。

### 尚未固化的实现细节

模块名、内核协议、profile 裁剪、模型选择、VibeKey 键位、数据保留期限和预算默认值，由 M0 和 M1 的结果确定。本文不替代锁定版本后的接口契约和测试计划，也不涉及直接修改仓库代码。

### 总结

**以真实个人需求为起点，以语音与实体输入降低交互成本，以完整而受限的 agent loop 建立可靠协调，以结构化接口和现有适配连接既有工具，以本地部署和实体确认守住数据边界，以源码公开共建和有限合作维持项目。**

VibeWand 的长期价值不在于再做一个更大的 AI，而在于让用户已经选择的 AI 和软件更容易被找到、更准确地接收意图，并能够可靠地接力工作。
